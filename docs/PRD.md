# ytm2spotify — PRD (v0.1 초안)

> 상태: **v0.2 (Spike 반영)** · 작성일: 2026-10-12 · Spike 결과: [`docs/spikes/m0-report.md`](spikes/m0-report.md)

## 1. 배경 / 문제

YouTube Music에서 Spotify로 옮기려 할 때, 몇 년간 쌓은 **보관함 앨범·구독 아티스트·좋아요 곡**을 옮길 방법이 마땅치 않다.

- 기존 SaaS(Soundiiz, TuneMyMusic 등)는 대량 이전 시 유료이고, **자동 매칭 결과를 이전 전에 검토할 수 없다.** 잘못 매칭된 항목이 조용히 섞인다.
- GitHub의 오픈소스 도구는 대부분 **플레이리스트 단위**이며, 앨범/아티스트 이전이나 매칭 검토 UI가 없다.
- YT Music 좋아요에는 정식 음원이 아닌 **사용자 업로드(UGC) 영상**이 섞여 있어, 단순 검색 매칭으로는 품질이 낮다.

## 2. 목표 / 비목표

### 목표 (v0.1)
1. YT Music의 **보관함 앨범, 구독 아티스트, 좋아요 곡**을 Spotify로 옮긴다.
2. 이전 전에 **양쪽 보관함을 비교하고 매칭 결과를 사람이 검토**할 수 있다.
3. Spotify에 없는 곡도 **잃어버리지 않게 보존**한다.
4. **비개발자**도 Mac/Windows 실행 파일로 쓸 수 있다.

### 비목표 (v0.1에서는 하지 않음)
- 플레이리스트 이전 → v0.2
- Spotify → YT Music 역방향 → v0.3 (Spotify 개인정보 데이터 파일 `YourLibrary.json` 활용 예정)
- 다른 서비스(Apple Music, TIDAL, 멜론 등)
- 서버 운영 / SaaS 형태 (Spotify 정책상 불가 — §6 참고)
- 주기적 자동 동기화

## 3. 사용자

| 페르소나 | 설명 | 시사점 |
|---|---|---|
| **이주자 (주 타깃)** | YT Music을 수년간 쓰다 Spotify로 이동. 보관함 수백~수천 개. 비개발자일 수 있음 | 설치·설정이 쉬워야 하고, 대량 처리 및 중단 후 재개가 필요 |
| **본인 (첫 사용자)** | 개발자. 실제 데이터로 매칭 품질을 검증 | 매칭 품질 지표를 측정할 수 있어야 함 |

## 4. 사용자 시나리오

1. 사용자는 GitHub Releases에서 OS에 맞는 파일을 내려받아 실행한다. 브라우저에 로컬 화면이 열린다.
2. **설정 마법사**를 따라 ① YT Music 연결(브라우저 헤더 붙여넣기) ② Spotify 개발자 앱 생성 후 Client ID 입력 및 로그인을 진행한다.
3. **불러오기**를 누르면 양쪽 보관함이 로드된다. ("YTM 앨범 312 / Spotify 앨범 40" 등)
4. **매칭**이 진행되고, 항목이 다음 상태로 분류된다:
   - ✅ 이미 Spotify에 있음 → 건너뜀
   - 🟢 자동 매칭(높은 신뢰도) → 기본 체크
   - 🟡 검토 필요 / 대체곡 → 기본 체크 해제, 후보 중 선택
   - 🔴 찾을 수 없음 → 보존 대상
5. 사용자는 🟡 항목을 검토한다. 후보를 고르거나, 직접 검색하거나, 제외한다.
6. **적용**을 누르면 체크된 항목만 Spotify에 저장/팔로우된다. 진행률이 표시되고, 중단돼도 이어서 할 수 있다.
7. 이전되지 않은 곡은 **YT Music 플레이리스트("ytm2spotify – 이전 안 됨")** 또는 CSV로 보존한다.

## 6. 비기능 요구사항 / 제약

- **프라이버시:** 모든 데이터와 인증 정보는 사용자 PC에만 저장한다. 외부 서버는 없다.
- **보안:** 로컬 서버는 `127.0.0.1`에만 바인딩한다. 외부 웹페이지의 요청(CSRF, DNS rebinding)을 차단한다.
- **플랫폼:** macOS(Apple Silicon/Intel), Windows 10+.
- **규모:** 항목 5,000개 수준에서 동작한다. 캐시 덕분에 재실행은 빨라야 한다.
- **안전성:** 사용자가 명시적으로 승인하기 전에는 Spotify에 아무것도 쓰지 않는다. 기존 데이터를 삭제하는 기능은 없다.
- **Spotify 제약 (2026.02 정책):**
  - 개발자 앱 소유자는 Premium이어야 하고, 앱당 사용자는 5명이다. → **각 사용자가 자기 앱을 만든다(BYOK).**
  - 검색 결과는 최대 10개이다.
  - 저장/팔로우는 `PUT /me/library`로 통합되었다(URI 최대 40개).
- **YT Music 제약:** 비공식 API(`ytmusicapi`)를 쓰므로 언제든 깨질 수 있다. 의존성 버전을 고정하고, 오류 메시지로 안내한다.

## 7. 성공 지표

| 지표 | 목표 |
|---|---|
| 정식 음원(ATV/OMV) 자동 매칭 정확도 | ≥ 95% (잘못된 자동 매칭 ≤ 2%) |
| UGC 중 원곡 매칭 성공률 | 측정 후 설정 (Spike) |
| 검토가 필요한 항목 비율 | ≤ 15% |
| 첫 실행부터 이전 완료까지 시간 (항목 1,000개 기준) | ≤ 30분 |
| 본인 보관함 실제 이전 완료 | ✅ |

## 8. 리스크 / 확인할 가정 → Spike

| # | 가정 | 틀리면 | 확인 방법 |
|---|---|---|---|
| R0 | 사용자가 Spotify 개발자 앱을 만들 수 있다 | 배포 모델 붕괴 | ✅ 버튼은 숨겨져 있지만 `/dashboard/create`로 가능 |
| R1 | `PUT /me/library`로 **아티스트 팔로우**가 된다 (레퍼런스 문서 목록에 artist URI가 없음) | 아티스트 이전 불가 → 기능 재정의 | ✅ 동작 확인 |
| R2 | Dev 모드 앱 + PKCE + `http://127.0.0.1` 리디렉트가 동작한다 | 인증 방식 변경 | ✅ (단 `market=from_token`은 403) |
| R3 | ytmusicapi로 앨범/구독/좋아요가 **전부** 페이지네이션된다 | 누락 발생 | ✅ (좋아요 차이는 사용할 수 없는 영상) |
| R4 | 좋아요 곡의 UGC 비중과 제목 파싱 매칭률 | UGC 전략 수정 | ✅ UGC 26%, 단순 매칭은 오탐 많음 |
| R5 | 검색 limit 10으로 후보가 충분하다 | 매칭률 저하 | ✅ limit 10 확인 |

## 10. 열린 질문

- Q1. 기술 스택 → **Python 확정** (근거: `ytmusicapi`가 Python 전용). ADR-001로 기록 예정.
- Q2. UI 방식: 로컬 웹(브라우저) vs 데스크톱 앱(Tauri 등) → 설계 단계에서 결정.
- Q3. 아티스트 동명이인 처리: 앨범 매칭 결과를 아티스트 판별에 활용할지.
