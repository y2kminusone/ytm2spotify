# ytm2spotify — 설계 문서 (초안)

> 상태: **작성 중** · 관련: [PRD](PRD.md), [Spike 리포트](spikes/m0-report.md)

## 1. 전체 구조

```
[YT Music] ⇄ YTMusicAdapter ⇄ [ 공통 모델 · 매칭 엔진 · 상태 저장 · UI ] ⇄ SpotifyAdapter ⇄ [Spotify]
```

- **어댑터:** 서비스별 차이(인증, 페이지네이션, 배치, 재시도, 필드 형식)를 숨기고 공통 인터페이스(`MusicService`)를 제공한다.
- **코어:** 공통 모델만 다룬다. 어떤 서비스인지 알지 못한다.
  → 역방향(v0.3)과 다른 서비스 추가 시 어댑터만 추가한다. 테스트는 가짜 어댑터로 한다.

```python
class MusicService(Protocol):
    def get_albums(self) -> list[Album]: ...
    def get_artists(self) -> list[Artist]: ...
    def get_liked_tracks(self) -> list[Track]: ...
    def search(self, query: SearchQuery) -> list[Album | Artist | Track]: ...
    def save(self, items: list[Album | Artist | Track]) -> SaveResult: ...
```

## 2. 데이터 모델

### 2.1 공통 모델 (어댑터 출력)

```python
@dataclass
class Album:   service: str; id: str; title: str; artists: list[str]; year: int | None; track_count: int | None
@dataclass
class Artist:  service: str; id: str; name: str
@dataclass
class Track:   service: str; id: str; title: str; artists: list[str]; album: str | None
               duration_s: int | None; isrc: str | None; video_type: str | None  # YTM 전용: ATV/OMV/UGC
```

### 2.2 매칭 레코드: 기계 판단 / 사람 결정 / 적용 결과를 분리

| 칸 | 값 | 정하는 주체 |
|---|---|---|
| `match_status` | `exists`(이미 있음) / `auto`(자동 매칭) / `review`(검토 필요) / `substitute`(대체곡) / `not_found`(못 찾음) | 매칭 엔진 |
| `decision` | `pending`(미정) / `accept`(+후보 id) / `skip`(건너뛰기) / `preserve`(이전 안 됨 목록으로) | 사용자 |
| `apply_status` | `none`(안 함) / `done`(완료) / `failed`(+사유) | 적용 단계 |

- 매칭을 다시 실행해도 `decision`은 덮어쓰지 않는다. (`pending`인 항목만 갱신)
- 적용은 `decision=accept AND apply_status!=done`인 항목만 대상으로 하므로 **중단 후 재개가 자연스럽다.**
- "자동 매칭을 사람이 바꾼 비율" 같은 품질 지표를 바로 계산할 수 있다.
- 초기 기본값: `auto` → `accept`, `exists` → `skip`, `not_found` → `preserve`, `review`/`substitute` → `pending`. **UGC는 `auto`여도 `pending`이다** (Spike R4).

### 2.3 저장소: SQLite → [ADR-002](adr/002-sqlite-state-store.md)

사용자 데이터 폴더의 `ytm2spotify.db` 파일 하나에 저장한다. (Mac `~/Library/Application Support/ytm2spotify/`, Windows `%APPDATA%\ytm2spotify\`)

```sql
items        (key PK, kind, service, payload JSON, first_seen, last_seen, removed)
             -- key = "{service}:{kind}:{id}", 양쪽 보관함 스냅샷
matches      (source_key PK → items, match_status, candidates JSON, matcher_version,
              decision, chosen_key, apply_status, apply_error, updated_at)
search_cache (query_hash PK, response JSON, fetched_at)   -- Spotify 검색 결과 캐시
meta         (k PK, v)                                     -- 스키마 버전, 마지막 동기화 시각, market 등
```

인증 정보(쿠키, 토큰)는 DB에 넣지 않고 별도 파일(권한 600)에 둔다 → §7.

## 3. 전체 흐름

```
① 연결 → ② 불러오기(동기화) → ③ 매칭 → ④ 검토 → ⑤ 적용 → ⑥ 보존/결과
```

### 3.1 다시 실행할 때: 이어서 하기

② 불러오기를 할 때마다 양쪽 보관함을 새로 읽어 `items`와 비교한다:

| 경우 | 처리 |
|---|---|
| 새로 생긴 YTM 항목 | `items`에 추가 → 매칭 대상 |
| 이미 있는 항목 | `last_seen`만 갱신, 기존 결정 유지 |
| YTM에서 사라진 항목 | `removed=1` 표시 (삭제하지 않음). 검토 목록에서 숨긴다 |
| Spotify에 새로 생긴 항목 | 아직 `pending`인 매칭 중 해당 항목과 일치하는 것을 `exists`로 바꾼다 |

화면에는 "새 항목 12개가 추가됐어요"처럼 변경분을 알려준다.

### 3.2 화면 상태를 어디에 저장하나

| 상태 | 저장 위치 | 이유 |
|---|---|---|
| 검토 결정(승인/건너뛰기/보관, 선택한 후보) | SQLite (`matches`) | 데이터다. 앱을 껐다 켜도, 다음 실행에도 유지돼야 한다 |
| 보고 있는 화면(탭, 필터) | **URL 쿼리** (`?tab=track&filter=todo`) | 새로고침·뒤로 가기에도 같은 화면으로 돌아온다 |
| 일괄 승인 기준 점수 | SQLite `meta` | 사용자 설정이다 |
| 선택된 행, 펼친 후보 목록 | 메모리 | 일시적 상태라 저장하지 않는다 | 처음부터 다시 하고 싶으면 **"처음부터 다시 하기"**(DB 초기화)를 쓴다.

## 4. 매칭 알고리즘

### 4.1 파이프라인

```
① 이미 있나? → ② 분류 → ③ 검색어 생성 → ④ 점수 → ⑤ 상태 결정
```

| 단계 | 내용 | 근거 |
|---|---|---|
| ① 이미 있나? | 불러온 Spotify 보관함과 로컬에서 비교한다(API 호출 없음). 일치하면 `exists` | 호출 절약 |
| ② 분류 (곡) | `video_type`이 ATV/OMV/OFFICIAL_SOURCE_MUSIC이면 일반 경로. UGC면 제목을 "아티스트 - 곡명"으로 파싱한다. **괄호를 제거하기 전에 원본 제목에서 변형 키워드를 감지한다** | Spike R4: 커버/리믹스가 원곡과 1.00으로 오탐 |
| ③ 검색어 | 항목당 최대 3개를 순서대로 시도하고, 충분한 후보가 나오면 멈춘다: 필드 검색(`track:… artist:…`) → 일반 검색 → 별칭 검색(`한글 (English)` 형태면 각 표기로) | Spike R4: `희대의 (HEEDAE)`, 로마자 표기 미탐 |
| ④ 점수 | §4.2 | |
| ⑤ 상태 | §4.3 | |

**변형 키워드(초안):** `cover`, `커버`, `remix`, `리믹스`, `live`, `라이브`, `ver.`, `version`, `acoustic`, `inst`, `sped up`, `slowed`, `직캠`, `fancam`, `무대`, `stage`, `edit`, `mashup`, `flip`. 이 목록은 정답셋으로 튜닝한다.

### 4.2 점수

**정규화:** NFKC → 소문자 → 공백·문장부호 제거 후 비교한다(`서울전자음악단` = `서울 전자 음악단`). 판 정보(Deluxe, Remaster 등)와 `feat.` 구간은 별도로 추출해서 비교한다.

| 종류 | 신호 (가중치는 정답셋으로 튜닝) |
|---|---|
| 앨범 | 앨범명, 아티스트, 발매연도(±1년 부분 점수), 트랙 수 |
| 아티스트 | 이름, 검색 순위. **동명이인은 내 보관함 앨범의 아티스트와 겹치면 가산점** |
| 곡 | 곡명, 아티스트, 앨범명, **재생 시간(±3초 일치, ±10초 초과 시 감점)** |

> **주의 (시안 작업에서 발견):** 뮤직비디오(OMV, UGC의 MV 재업로드)는 인트로/아웃트로 때문에 음원보다 20~30초 긴 경우가 흔하다(예: Labi Siffre "My Song" MV 4:21 vs 음원 4:44, 23초 차). 영상 유형에서는 길이 신호의 가중치를 낮추고, 길이 차이만으로 `not_found` 처리하지 않는다. 정식 음원(ATV)끼리는 강한 신호로 쓴다.

**여러 판 처리 (Q4 결정):** YTM 제목에 판 정보가 있으면 판까지 일치하는 후보를 우선한다. 없으면 **일반판을 우선**하고, 트랙 수가 같으면 가산점을 준다.

각 후보에는 **판단 근거**(예: "곡명 일치 · 길이 2초 차 · 아티스트 일치")를 같이 저장해서 검토 화면에 보여준다.

### 4.3 상태 결정과 커트라인

| 조건 | `match_status` | 초기 `decision` |
|---|---|---|
| 변형이 감지됨, 원곡 후보 있음 | `substitute` | `pending` |
| 점수 ≥ `T_auto` | `auto` | `accept` (**UGC는 `pending`**) |
| `T_review` ≤ 점수 < `T_auto` | `review` | `pending` |
| 점수 < `T_review` 또는 후보 없음 | `not_found` | `preserve` |

**원칙 (Q3 결정): 기본은 보수적으로, 검토는 빠르게.**
- 기본 `T_auto`는 높게 둔다. 잘못 저장된 항목은 1,500개 중에서 찾아내기 어렵고, 한 번 보이면 결과 전체에 대한 신뢰가 떨어진다.
- 대신 검토를 빠르게 한다 → §5: 점수순 정렬, **"이 점수 이상 모두 승인" 일괄 버튼**, 판단 근거 표시, 키보드 단축키, 유사 항목 묶음 처리.

### 4.4 커트라인 보정 (데이터 기반)

"커트라인"이 낮을수록 자동 승인이 많아진다(느슨). 목표는 **오탐률 ≤ 2%(PRD §7)를 지키는 가장 낮은 `T_auto`**, 즉 안전한 범위에서 검토를 최소화하는 값이다.

| 단계 | 방법 | 서버 |
|---|---|---|
| v0.1 초기값 | 개발자 본인 보관함으로 만든 **정답셋**(F16)으로 커트라인을 정한다 | 없음 |
| v0.1 개인 보정 | 사용자가 자동 매칭을 바꾸거나 해제한 기록 = 오탐 라벨. 이것으로 그 사용자에게 맞는 커트라인을 **로컬에서 제안**한다 ("검토 결과로 보면 0.85로 낮춰도 안전해요") | 없음 |
| v0.2 익명 통계 공유 (선택) | "매칭 통계 내보내기": **곡명 없이** 점수, 종류, 자동 여부, 사용자 수정 여부만 담은 파일. 원하는 사용자만 GitHub Issue에 첨부한다 → 모이면 기본값 갱신 (F20) | 없음 |
| 이후 (사용자 증가 시) | 동의한 사용자만 익명 통계 자동 전송 (서버리스) | 최소 |

`matches.matcher_version`으로 어떤 알고리즘 버전이 매긴 점수인지 기록한다. 버전이 오르면 `pending` 항목만 재매칭한다.

### 4.5 API 호출 예산

- 항목당 검색 최대 3회, 검색 결과는 `search_cache`에 저장한다 → 재실행 시 0회.
- 본인 데이터 기준(앨범 218 + 아티스트 8 + 좋아요 1,250 − 이미 있는 항목) 대략 1,500~3,000회. 429를 받으면 `Retry-After`만큼 대기한다.
- 처리 속도는 M1에서 측정한다.

## 5. 화면 흐름 / 디자인

### 5.1 디자인 원칙

이 앱의 성격: **몇 년 모은 음반을 새 집으로 옮겨주는 이사 도우미.**

1. **안심이 먼저:** "잃어버리는 곡 없음"이 핵심 가치다. 진행 상황과 결과는 항상 숫자로 보여주고, 되돌릴 수 없는 동작(적용) 전에는 무엇이 일어날지 요약한다.
2. **화면 하나에 할 일 하나:** 설정 마법사와 결과 화면은 한 단계에 질문 하나, 큰 글씨, 넉넉한 여백으로 만든다(토스 디자인 원칙 참고, 브랜드는 차용하지 않음).
3. **촘촘하지만 읽기 쉽게:** 검토 화면은 정보가 많으므로 밀도를 유지하되, 위계(제목 > 보조 정보 > 근거 태그)와 정렬로 읽기 쉽게 한다.
4. **앨범 아트로 알아본다:** 텍스트보다 커버 이미지가 먼저 눈에 들어오게 한다.
5. **색은 의미로만 쓴다:** 기본은 밝고 차분한 중립색에 포인트 색 하나를 둔다. YouTube 빨강과 Spotify 초록은 **출처 표시용 작은 요소**로만 쓴다. 상태 색(성공/주의/위험)은 일관되게 쓴다.
6. **밝은 테마가 기본**이고, OS 설정을 따라 다크 모드를 지원한다.
7. **친근한 문구:** "~해요"체, 기술 용어 대신 결과 중심 표현을 쓴다. ("PUT 실패" ✗ → "3개는 저장하지 못했어요. 다시 시도할까요?" ✓)

### 5.2 화면 목록

설정 마법사 → 대시보드(불러오기·매칭 진행) → **검토** → 적용 진행 → 결과·보존

- v0 (기능 확인용, 폐기 예정): [`wireframes/review.html`](wireframes/review.html)
- v1: [`spikes/astryx-ui`](../spikes/astryx-ui) — Astryx(React) 기반, `npm run dev`로 실행. 샘플 데이터는 `scripts/make_sample.py`로 생성한다(개인 데이터라 git 제외).

**v1 피드백 반영 기록 (2026-10-12)**

| 피드백 | 원인 | 조치 |
|---|---|---|
| 테마 A(Neutral) / B(Butter) 중 A 선호 | — | **Neutral 테마 확정** |
| 점수 연결선이 애매하다 | "97"이 무엇의 97인지 불명확하고, 사용자가 원하는 건 숫자가 아니라 판정이다 | 가운데를 `→` 화살표 + **판정 라벨**(확인 필요/다른 버전)로 바꾸고, 점수는 "일치도 97%"로 작게 표시 |
| 왜 어떤 곡만 점선 테두리인가 | 점선(= 다른 버전)의 의미가 화면에서 읽히지 않는다. 태그와 정보가 중복된다 | 점선 제거. 의미는 판정 라벨과 태그로만 전달 |
| "직접 검색"이 뭔가 | 누르면 바로 검색이 실행될 것처럼 읽힌다 | **"다른 곡 찾기"** + 돋보기 아이콘으로 변경 |
| 선택된 행이 잘 안 보인다 | 왼쪽 3px 선만으로는 약하고, 이어서 쓴 회색 배경은 페이지 배경과 같은 색이었다 | 페이지(회색)·카드(흰색)와 겹치지 않는 **옅은 파란색** 배경 + 파란 테두리 + 그림자. 호버는 배경 대신 그림자로 구분 |
| 제목 말줄임 툴팁에 "사용자 업로드"가 섞인다 | 배지가 제목 텍스트 안에 있었다 | 배지를 제목에서 분리해 아래 정보 줄로 이동 |
| 좌우 제목 줄이 안 맞는다 | 배지가 제목 위에 있고, 양쪽이 세로 가운데 정렬이었다 | 제목/아티스트/정보 순서를 좌우 동일하게 맞추고 위쪽 정렬, 제목은 1줄로 고정 |
| 행에 호버 효과가 있으면 좋겠다 | — | 호버 시 배경색과 테두리 강조 |
| 판정(상태)이 한눈에 안 들어온다, 긴 제목이 잘린다 | 판정이 가운데 화살표 아래에 작게 있었고, 버튼 4개가 같은 줄에서 가로 공간을 차지했다 | 행을 3단으로 재구성: **① 맨 위 판정 + 일치도 + 내 결정 요약** ② YT Music → Spotify 비교(제목 전체 표시) ③ 아래 줄에 승인/건너뛰기/보관 + 다른 곡 찾기. 대가: 한 화면에 보이는 행 수가 줄어든다(약 5 → 3) |
| 슬라이더를 움직이면 목록에 바로 반영됐으면 | 개수만 버튼에 바뀌었다 | 슬라이더를 움직이면 기준을 넘는 행에 "OO점 이상이라 일괄 승인 대상이에요" 표시 + 초록 테두리, 상단 집계에 "+N 예정"과 빗금 막대로 미리보기 |
| "다른 곡 찾기"만 떨어져 있고 테두리가 없다 | 오른쪽 끝에 고스트 버튼으로 따로 있었다 | 결정 버튼 옆에 구분선을 두고 같은 모양의 테두리 버튼으로 묶음 |
| 집계(저장/보관/건너뜀/확인 전)가 맨 아래라 안 보인다 | 하단 바에 작은 글씨로 있었다 | **상단 고정 집계 바**로 이동 + 비율 막대. 하단 바에는 단축키와 저장 버튼만 남김 |
| 커버곡/리믹스/길이 태그, "사용자 업로드" 배지 색과 위치가 제각각이라 지저분하다 | 근거 태그가 오른쪽 정보 안에, 업로드 배지는 왼쪽 정보 안에 섞여 좌우 대칭이 깨졌고 색이 4종(노랑/주황/빨강/초록) | 좌우는 **제목/아티스트/앨범·길이 3줄로 완전 대칭**(YTM에 앨범이 없으면 "앨범 정보 없음"). 근거는 비교 아래 **한 줄의 중립색 칩**으로 모으고 심각도는 작은 아이콘 색만으로 표시(문제 → 맞는 점 순). "커버곡이라 원곡으로 대체해요"처럼 버전 정보는 판정 옆 문장으로 이동 |
| 긴 제목(예: "Post Malone - Circles (cover by Zior Park, Sion Jung, Han-Bin Kim)")이 줄바꿈되면 좌우 줄이 어긋난다 | 좌우가 각자 독립된 블록이라 한쪽 제목이 두 줄이 되면 아래 줄이 밀렸다 | CSS **subgrid**로 좌우가 제목/아티스트/정보 **행을 공유**하게 함. 제목은 최대 2줄(넘치면 말줄임 + 툴팁) |
| 근거 칩을 결정 버튼 줄 오른쪽으로 | — | 이동. 버튼(왼쪽)과 근거(오른쪽)가 한 줄에 |
| 위쪽 집계도, 아래 단축키 바도 눈에 안 들어온다 | 화면 가장자리의 얇은 띠라 시선이 가지 않았다 | **오른쪽 고정 사이드 패널**로 통합: 진행 상황(막대 + 큰 숫자 4개) → 한 번에 승인(슬라이더) → 단축키 → 저장 버튼. 좁은 화면에서는 하단 고정 요약으로 접힘 |
| 사이드 패널에서 "키보드로 빠르게"가 가장 먼저 눈에 띈다 | 키 배지(진한 테두리 박스)가 세로로 5개 쌓여 패널에서 시각적 무게가 가장 컸다 | 시선 순서대로 재배치: **① 진행 상황 문장("확인할 항목이 7개 남았어요") + 막대 + 숫자 + 저장 버튼** → ② 한 번에 승인 → ③ 단축키는 **접힌 상태**로 맨 아래 |
| 스크롤할 때 사이드 패널이 화면에 딱 붙어 있어 딱딱하다 | `position: sticky`만 써서 움직임이 전혀 없었다 | 스크롤 방향 반대로 최대 12px(첫 값 18px) 살짝 뒤따라오다 **스프링처럼 천천히 제자리로 돌아오는** 관성 효과(강성 0.06, 감쇠 0.8. 첫 값 0.14/0.74는 너무 빨랐음) + 스크롤 중 그림자 강화. `prefers-reduced-motion`이면 끔, 좁은 화면(하단 바)에서도 끔 |
| "Spotify에 없음" 항목의 눌린 "보관" 버튼 색이 이상하다(진한 갈색 위 검정 글씨) | Neutral 테마의 `--color-warning`은 **글자/아이콘용 진한 올리브색(#4b3900)**인데 배경색으로 썼다. 같은 실수가 보관 막대, 주의 아이콘, "확인 전" 숫자에도 있었다 | 앱 전용 색 토큰 `--keep`(앰버 채우기) / `--keep-soft`(옅은 배경) / `--keep-ink`(강조 글자)를 정의하고 교체. 다크 모드 값도 함께 지정. **교훈: 디자인 시스템 토큰은 이름이 아니라 용도(fill/text/icon)를 확인하고 쓴다** |
| 새로고침하면 필터(예: 확인 필요)가 초기화된다 | 탭/필터가 메모리에만 있었다 | 탭과 필터를 URL에 동기화(§3.2). 시안의 결정 내용은 샘플이라 새로고침 시 초기화되지만, 실제 앱은 SQLite에 저장한다 |
| 사이드 패널을 조금 내려 달라: 핵심 콘텐츠는 비교 카드인데, 패널이 제목("좋아요 곡 5개만 확인해 주세요")과 같은 높이에서 시작해 시선이 분산된다 | 패널이 페이지 머리말과 같은 열 구조 안에 있었다 | 레이아웃을 2단으로 재구성: **머리말(제목, 탭, 필터)은 전체 폭**, 그 아래에서 **목록과 패널이 같은 높이로 시작** |
| 승인/건너뛰기/보관 버튼에 호버 효과가 없다(눌러야 반응을 안다) | 버튼 배경을 직접 지정하면서 Astryx 기본 호버 오버레이를 덮어썼다 | 호버(배경 + 테두리 진하게), 누름(1px 내려감), 눌린 상태별 호버 색, 키보드 포커스 링 추가. **교훈: 컴포넌트 스타일을 덮어쓰면 상호작용 상태(hover/active/focus)도 직접 책임져야 한다** |
| 카드 호버가 너무 옅다 | 테두리 한 단계 + 얕은 그림자뿐이었다 | 테두리를 더 진하게, 그림자를 깊게, **2px 떠오르는 움직임** 추가(선택된 카드 제외, 동작 줄이기 설정 시 움직임 끔) |
| "Spotify에 12개 저장하기" 버튼에 호버 효과가 없다 | 테마의 호버 효과는 "버튼 위에 5% 검정 덮기"라서, 거의 검정(#1b1b1b)인 기본 버튼에서는 보이지 않는다. 회색 버튼에서도 매우 옅다 | 저장 버튼은 호버 시 **밝아지고** 그림자가 생기게, 패널·묶음 처리의 회색 버튼은 진한 배경 + 테두리로 호버 표시. 모두 누를 때 1px 눌림 |
| Spotify 쪽에 곡 길이가 없어 비교가 안 된다 | Spotify도 `duration_ms`를 주지만 표시하지 않았다 | 오른쪽도 제목/아티스트/**앨범·길이**로 왼쪽과 대칭. 길이 차이 근거는 실제 값으로 계산 |

교훈: 색, 선, 테두리 같은 **암묵적 시각 기호는 설명 없이는 전달되지 않는다.** 의미는 글자로 쓰고, 시각 기호는 보조로만 쓴다.
