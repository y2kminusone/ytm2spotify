# ADR-004: 데스크톱에서 실행하는 로컬 웹앱으로 만든다

- 상태: Accepted
- 날짜: 2026-10-13

## 맥락

비개발자도 쓸 수 있어야 한다(PRD §2). 배포 형태로 네 가지를 검토했다. 비교 기준은 **처음 쓰는 사람이 이전을 끝내기까지의 장벽**이다.

v0.0.1은 이미 로컬 웹앱 형태로 만들어 실사용했다. Python 서버(FastAPI, `127.0.0.1` 전용)가 SQLite와 매칭 엔진을 갖고, 브라우저가 React 화면을 띄운다.

## 검토한 대안

| | ① 호스팅 웹사이트 | ② 로컬 웹앱 | ③ 데스크톱 앱 | ④ 폰 앱 |
|---|---|---|---|---|
| 시작 | 주소만 열면 됨 | 실행 파일 → 브라우저 탭 | 실행 파일 → 앱 창 | 스토어 설치 |
| 설치 경고 | 없음 | 서명 전엔 OS 경고 1회 | 서명 전엔 OS 경고 1회 | 없음(심사 통과 시) |
| Spotify 연결 | 가능 | 가능 | 가능 | 가능하나 폰에서 개발자 앱 만들기가 불편 |
| **YT Music 연결** | ❌ 사용자 쿠키를 **우리 서버로 받아야** 함 | ✅ | ✅ | ❌ 구글이 앱 내 웹뷰 로그인을 차단하고, 폰에는 개발자 도구가 없음 |
| 데이터 위치 | 우리 서버 | 사용자 PC | 사용자 PC | 사용자 폰 |
| 검토 작업(수백 개 비교) | 적합 | 적합 | 적합 | 화면이 좁아 부적합 |
| 배포 장벽 | 서버 운영 비용, 신뢰 | 코드 서명(선택) | 코드 서명(선택) | **스토어 심사 거절 가능성**(비공식 YouTube 접근), Apple $99/년 |
| 구현 | 서버 운영 필요 | **이미 동작** | ②에 창 껍데기 추가 | `ytmusicapi`(Python) 재구현 필요 |

### ①을 배제한 이유
YT Music은 공식 API가 없어 로그인 쿠키로 접근한다(ADR-001). 웹사이트는 브라우저 보안 정책 때문에 YT Music에 직접 요청할 수 없으므로, 사용자 쿠키를 서버로 보내야 한다. 남의 구글 로그인 쿠키를 받는 서비스는 피싱과 구분되지 않고, 서버발 요청은 구글이 차단할 가능성이 높다. Spotify 개발 모드 정책(앱당 사용자 5명)과도 맞지 않는다.

### ④를 배제한 이유
가장 위험한 부분(YT Music 연동)을 다시 구현해야 하고, 그 결과물이 스토어 심사를 통과하지 못할 수 있다. 보관함 이전은 평생 한두 번 하는 작업이라, PC에서 한 번 실행하고 끝내는 흐름이 더 자연스럽다.

## 결정

**② 로컬 웹앱**으로 한다. 배포는 실행 파일을 더블클릭하면 서버가 뜨고 브라우저 탭이 열리는 형태로 한다(PyInstaller, 웹 빌드 포함).

## 근거

- 초기 세팅의 진짜 장벽은 설치가 아니라 **연결**이다(Spotify 개발자 앱 약 5분, YT Music 헤더 복사 약 3분). 이 장벽은 ②, ③, ④ 모두 같다. 그러므로 ②와 ③의 접근성 차이는 거의 없다.
- ②는 이미 실사용으로 검증됐다(2026-10-13, 391개 이전).
- 화면 코드를 그대로 두고 ③(pywebview/Tauri 창)으로 옮길 수 있어, 결정을 되돌리는 비용이 낮다.

## 결과

- (+) 계정 정보와 데이터가 사용자 PC 밖으로 나가지 않는다. 서버 운영 비용이 없다.
- (+) Mac/Windows를 같은 코드로 지원한다.
- (−) 서명하지 않은 실행 파일은 OS 경고가 뜬다 → 안내 문서로 대응하고, 사용자가 늘면 서명을 검토한다.
- (−) "브라우저 탭을 닫으면 앱이 꺼진 줄 안다"는 혼란이 생길 수 있다 → 피드백이 오면 ③으로 전환한다.
- (−) 서버가 `127.0.0.1`에 열리므로 다른 웹페이지의 요청을 막아야 한다 → Host 헤더 검사(DNS rebinding 방지)와 쓰기 요청의 사용자 정의 헤더 검사(CSRF 방지)로 해결했다.
- 접근성을 더 올릴 지렛대는 배포 형태가 아니라 **YT Music 연결을 쉽게 하는 것**이다(예: 크롬 확장으로 한 번에 연결). ROADMAP에 기록했다.
