# ADR-005: 매칭 자동 재개는 "앱이 켜져 있는 동안 기다렸다가 이어서" 한다

- 상태: Superseded by [ADR-006](006-stop-project.md) (구현하지 않음)
- 날짜: 2026-10-13

## 맥락

첫 실사용에서 Spotify Development 모드 앱의 **검색 일일 할당량**이 드러났다(Spike R6). 검색 약 540회 후 `429 QUOTA_EXCEEDED`가 왔고, `Retry-After`는 약 22.5시간이었다. 같은 시점에 저장·보관함 읽기 등 다른 엔드포인트는 정상이었다.

남은 좋아요 1,034곡에는 검색 절약(모음 영상 생략, 이미 매칭된 앨범의 수록곡 재사용)을 적용해도 900~1,000회의 검색이 필요하다. 곡이 많은 사용자는 **2~3일에 걸쳐 매칭**할 수밖에 없다. 매일 사용자가 직접 다시 실행하게 할 수는 없다.

v0.0.1은 할당량 초과를 감지하면 즉시 멈추고 리셋 시각을 저장한다. 재개는 사람이 `ytm2spotify match`를 다시 실행해야 한다.

## 검토한 대안

| | A. 앱 실행 중 대기 후 재개 | B. OS 예약 작업 | C. 클라우드에서 실행 |
|---|---|---|---|
| 방식 | 로컬 서버가 리셋 시각까지 기다렸다가 매칭을 이어감. 앱 시작 시 리셋이 지났으면 바로 재개 | Mac launchd / Windows 작업 스케줄러에 일회성 작업 등록 | 우리 서버가 대신 실행 |
| 앱을 꺼도 진행 | ✗ | ✓ (PC가 켜져 있으면) | ✓ |
| 구현 | 반나절. 플랫폼 공통 | OS별 코드, 등록·해제·권한 처리 | 서버 필요 |
| 사용자 동의 | 불필요 | PC에 예약 작업을 남기므로 필요 | 계정 정보를 서버로 보내야 함 |
| 정책 충돌 | 없음 | 없음 | ADR-004(데이터는 PC 밖으로 나가지 않음)와 충돌 |

## 결정

**A**로 한다. 같이 다음을 만든다.

- **매칭 화면:** 진행률, 할당량 상태, "다음 매칭: 22:43 (n시간 남음)" 카운트다운, 끝나면 데스크톱 알림
- 새로 매칭된 항목은 바로 검토 화면에 추가된다 → "매일 조금씩 검토하고 저장"하는 흐름
- 할당량 숫자는 하드코딩하지 않는다. 문서화되지 않았고 바뀔 수 있으므로 **429 응답과 `Retry-After`로 감지**한다

## 근거

- 매칭은 할당량 안에서 몇 분이면 끝나므로(초당 약 10건), 앱을 켜 두기만 하면 하루 한 번 돌기에 충분하다.
- 노트북을 덮었다 열어도 앱이 켜져 있으면 깨어난 직후 리셋 시각이 지났는지 확인하고 이어서 할 수 있다.
- B는 v0.4 자동 동기화(ROADMAP 장기 비전)에서 어차피 필요해진다. 그때 상주 앱과 함께 설계하는 것이 중복이 적다.

## 결과

- (+) 사용자가 매일 다시 실행할 필요가 없다(앱을 켜 두는 경우).
- (+) 플랫폼 공통 코드 하나로 끝난다.
- (−) 앱을 끄면 멈춘다 → 매칭 화면과 결과 화면에서 "앱을 켜 두면 22:43에 자동으로 이어서 해요"라고 명확히 안내한다.
- (−) 실제로 불편하다는 피드백이 나오면 B를 다시 검토한다.
